# Audit ERP GSP — 30 Oktober 2026

## Kesimpulan

Proyek merupakan fondasi ERP modular dengan pencatatan dasar, belum ERP operasional yang menyelesaikan proses bisnis dari awal sampai akhir. Fondasi layak dilanjutkan; transaksi keuangan dan kontrol persetujuan bisnis perlu dibangun sebelum penggunaan produksi untuk proses tersebut.

Audit mencakup seluruh source aplikasi, konfigurasi proyek, dua migration SQL, autentikasi, kebijakan akses, tampilan berbasis kode, dokumentasi, serta pemeriksaan kompilasi. Tidak ada perubahan fitur atau migration database dalam audit ini.

**Batas bukti:** database Supabase aktif, konfigurasi Auth di dashboard, data produksi, hak akses aktual, deployment, backup, dan perilaku browser dengan akun tiap peran belum diverifikasi. Temuan SQL menjelaskan perilaku yang ditetapkan migration repository, bukan bukti bahwa migration tersebut sudah diterapkan di server. Tidak ada klaim bahwa dependency bebas kerentanan; pemeriksaan advisori dependency belum dijalankan.

## Yang sudah tersedia

- Next.js 16.4.3, React 19, TypeScript strict, Tailwind, layout desktop dan navigasi mobile.
- Login email/password, logout, verifikasi user server, refresh cookie sesi melalui proxy.
- Organisasi dan tujuh peran: owner, director, finance, hr, operations, auditor, staff.
- Sebelas tabel: organisasi, membership, registri integrasi, approval, audit, serta enam tabel modul.
- RLS di seluruh tabel yang didefinisikan; pembatasan baca keuangan, SDM, dan pajak.
- Foreign key gabungan untuk mencegah relasi proyek–klien dan pekerjaan–proyek lintas organisasi.
- RPC approval dengan pengecekan peran, larangan persetujuan sendiri, penguncian row, keputusan dan audit dalam satu transaksi.
- Trigger audit insert/update/delete pada enam tabel modul; klien authenticated tidak diberi izin DML langsung pada audit log.
- Constraint enum, kode unik per organisasi, nilai pajak nonnegatif, dan urutan tanggal proyek.
- README, contoh konfigurasi environment, lint, typecheck, dan build scripts.

## Temuan prioritas tinggi

### A01 — Approval belum mengendalikan transaksi bisnis

**Bukti:** `src/app/(workspace)/modul/actions.ts:60` langsung insert ke tabel modul. Tidak ditemukan alur pengajuan approval di source. `supabase/migrations/202610290001_foundation.sql:214` hanya mengubah approval_requests dan menambahkan audit; tidak menerapkan keputusan ke record bisnis.

**Dampak:** keberadaan halaman persetujuan belum menjamin suatu transaksi harus diperiksa sebelum berlaku. Data modul juga mendapat izin update/delete bagi peran penulis melalui Data API, walaupun tombolnya belum tersedia.

**Bangun:** state machine draft → submitted → approved/rejected → executed/posted sesuai tipe dokumen; aturan transisi dan penguncian record di database; eksekusi keputusan secara atomik; cegah eksekusi ganda; revisi dokumen membatalkan persetujuan versi sebelumnya.

**Selesai bila:** transaksi wajib persetujuan tidak bisa dieksekusi melalui UI maupun API langsung sebelum disetujui; keputusan paralel hanya berhasil sekali; revisi tidak memakai approval lama.

### A02 — Pembuat request dapat memilih pemeriksa dan referensi secara bebas

**Bukti:** migration foundation baris 43–49 dan 144–153. Policy insert memeriksa pengaju, membership, dan status awal, tetapi tidak menentukan required_role berdasarkan kebijakan bisnis. record_type/record_id berupa teks tanpa pemeriksaan keberadaan, organisasi, dan versi record sasaran.

**Dampak:** anggota dapat membuat request melalui API dengan jenis/referensi arbitrer dan memilih peran pemeriksa yang diizinkan enum. Ini belum mengeksekusi transaksi bisnis saat ini, tetapi berisiko saat approval dihubungkan ke transaksi.

**Bangun:** RPC submit per jenis dokumen, penentuan approver di server/database, validasi hak pengaju atas sasaran, organisasi, status, versi, dan larangan request aktif duplikat. Cabut insert bebas bila seluruh pengajuan melalui RPC.

### A03 — Metadata pembuat dan perpindahan organisasi belum dilindungi di database

**Bukti:** migration module memiliki created_by yang merujuk auth.users, sedangkan policy tulis memeriksa role organisasi saja. assigned_to juga hanya merujuk auth.users, tanpa constraint membership organisasi. UPDATE tersedia melalui grant dan policy FOR ALL.

**Dampak:** klien API dapat mengisi created_by milik user lain; assigned_to tidak menjamin penerima anggota organisasi. User yang berhak di dua organisasi dapat memindahkan record tanpa relasi penghalang ke organisasi lain karena tidak ada penguncian organization_id. Actor audit tetap berasal dari auth.uid(), sehingga pemalsuan created_by tidak berarti pemalsuan actor audit.

**Bangun:** created_by diisi/diperiksa database saat insert dan tidak boleh diubah; organization_id immutable pada data bisnis; assignment wajib ke anggota aktif organisasi. Terapkan operasi transfer eksplisit bila memang diperlukan.

### A04 — Audit belum cukup untuk menelusuri isi perubahan

**Bukti:** `supabase/migrations/202610290002_module_mvp.sql:264` hanya menyimpan module_key pada details. Tidak ada snapshot/diff before/after. Perubahan membership/peran dan pengajuan request tidak mempunyai trigger audit. Halaman audit mengambil actor_id tetapi tidak menampilkannya.

**Dampak:** diketahui siapa melakukan operasi dan record mana, tetapi isi perubahan atau data yang dihapus tidak dapat direkonstruksi dari audit tersebut. Perubahan hak akses belum terlacak di mekanisme ini.

**Bangun:** audit perubahan field yang relevan, actor, waktu, alasan, versi, request/correlation ID; audit membership dan submission; tampilkan detail yang mudah dibaca. Redaksi field sensitif dan kebijakan retensi harus disesuaikan dengan akses auditor.

### A05 — Hak akses CRUD terlalu umum untuk kontrol bisnis lanjutan

**Bukti:** policy FOR ALL dan grant SELECT/INSERT/UPDATE/DELETE pada seluruh tabel modul (`202610290002_module_mvp.sql:170–229`). Staff dapat mengubah/menghapus kontak dan pekerjaan lain dalam organisasi, bukan hanya milik atau penugasannya. Finance dapat mengubah status pajak langsung bila lewat Data API.

**Dampak:** menyembunyikan tombol UI tidak membatasi API. Status reviewed/reported belum dijamin melewati pemeriksaan bisnis.

**Bangun:** matriks hak per operasi, field dan status; pembatasan penugasan bila diperlukan; RPC untuk transisi sensitif; arsip/void untuk dokumen bisnis yang harus dipertahankan. Ini keputusan kebijakan perusahaan, bukan bukti kebocoran lintas organisasi.

### A06 — Pengujian keamanan dan alur bisnis belum tersedia

Tidak ditemukan test suite, test runner, pengujian SQL/RLS, atau workflow CI di repository. Lint dan kompilasi tidak membuktikan isolasi organisasi, pemisahan peran, maupun kebenaran transaksi.

**Bangun:** fixture dua organisasi dan tujuh peran; uji allow/deny langsung pada API/SQL untuk CRUD, approval sendiri, keputusan paralel, perubahan organisasi, pencabutan membership, dan perubahan record setelah approval. Tambahkan pengujian browser untuk alur bisnis yang dipilih serta CI lint/typecheck/build/test.

## Bug dan kekurangan perilaku yang terkonfirmasi dari kode

| Temuan | Bukti / dampak | Perbaikan |

| Form proyek tersedia untuk staff tetapi database menolak insert | writeRoles CRM memuat staff; ProjectForm memakai izin CRM yang sama. RLS crm_projects hanya owner/director/operations | Pisahkan izin kontak dan proyek, selaraskan UI, action dan RLS |
| Tidak ada edit, arsip, detail record, atau transisi status | Action modul hanya create; daftar tidak memiliki tindakan | Bangun siklus record lengkap dengan validasi hak dan konflik versi |
| Relasi ada di schema tetapi belum dipakai form | Form proyek tidak mengirim client_id; pekerjaan tidak mengirim project_id/assigned_to | Pilihan klien, proyek, penanggung jawab yang difilter organisasi |
| Tenggat tersimpan tetapi tidak ditampilkan di daftar | Query pekerjaan dan pajak tidak mengambil due_on | Tampilkan tenggat, overdue, filter dan pengingat |
| Akun keuangan selalu ditampilkan aktif | Pemetaan status konstan active, tidak membaca is_active | Baca is_active dan dukung penonaktifan yang sah |
| Kegagalan form modul dilempar sebagai exception | actions.ts menggunakan throw untuk validasi/duplikasi; belum ada state error form atau error boundary khusus | Kembalikan error field yang terstruktur, pertahankan input, tambahkan pending state |
| Potensi submit ganda | Form modul tidak mempunyai indikator pending/disable; beberapa tabel tidak punya natural-key/idempotency guard | Pending UI serta idempotensi untuk operasi bisnis yang memerlukannya |

| Daftar dibatasi tanpa pagination | CRM 50 per jenis; modul lain, approval, audit 100 | Pagination server, pencarian, filter, total count yang jelas |
| Pengguna tidak berhak dapat melihat tampilan kosong yang menyesatkan | RLS memfilter hasil; navigasi menampilkan semua modul; halaman audit tidak memeriksa role secara eksplisit | Tampilan akses ditolak yang jelas dan menu sesuai peran, tetap gunakan RLS |
| Tombol review tampil bagi semua pembaca request pending | queue.tsx hanya memeriksa status pending; RPC tetap menolak pengaju/peran salah | Tentukan canReview per user; tampilkan alasan bila tidak boleh |
| Reviewer tidak melihat bahan keputusan memadai | Tabel approval menampilkan jenis dan potongan ID, tanpa detail dokumen/nilai/lampiran/pengaju | Halaman detail approval, versi dokumen, lampiran dan riwayat |

| Setup memberi diagnosis yang terlalu umum | Saat configured, halaman selalu menyebut membership belum ditemukan, termasuk saat dibuka owner lewat dashboard | Pisahkan halaman pengaturan dan diagnosis berdasarkan pemeriksaan aktual |
| Notifikasi belum berfungsi | Tombol bell tanpa handler, sumber data, atau panel | Inbox notifikasi untuk approval dan tenggat |
| Timestamp pembaruan tidak diperbarui otomatis | updated_at hanya default now(); tidak ada trigger pembaruan | Trigger updated_at atau operasi tulis terpusat yang menjaminnya |

## Platform dan operasional yang perlu dibangun

1. **Administrasi:** undang/aktifkan/nonaktifkan anggota, reset password dan callback pemulihan, profil, pilihan organisasi. Lindungi owner terakhir dari dihapus/diturunkan dan audit perubahan peran. Inisialisasi owner saat ini manual lewat SQL Editor.
2. **Autentikasi sensitif:** kebijakan MFA untuk peran yang ditentukan, masa sesi, pencabutan akses, penanganan kegagalan Auth. Pengaturan CAPTCHA/rate limit/email produksi perlu diperiksa pada Supabase aktif; tidak dapat disimpulkan dari repository.
3. **Dokumen:** storage privat, akses per organisasi, metadata lampiran, batas jenis/ukuran, retensi dan tautan unduh berizin. Belum ditemukan implementasi storage.
4. **Database reproducible:** konfigurasi lingkungan lokal/staging, seed yang aman, pengujian migration dari database kosong dan upgrade, tipe TypeScript hasil schema. Saat ini belum ada config.toml, seed atau tipe database di repository.
5. **Deployment:** CI, staging/production terpisah, prosedur migration dan rollback/recovery, monitoring error, health check, serta runbook insiden. Ketiadaan file di repo bukan bukti bahwa fasilitas eksternal tidak ada.
6. **Recovery:** verifikasi backup dan uji restore pada layanan aktif, tentukan target pemulihan dan kehilangan data yang dapat diterima.
7. **Integrasi:** registri integration_sources sudah ada, tetapi belum ada connector, autentikasi provider, job sinkronisasi, idempotensi, retry, mapping atau rekonsiliasi. Bangun hanya setelah sumber yang akan diintegrasikan jelas.
8. **Pemeliharaan kode:** page modul sekitar 550 baris mencampur query/form/presentasi enam modul; matriks writeRoles diduplikasi. Pisahkan per modul dan pusatkan permission; tetap pertahankan kontrol database sebagai batas keamanan.
9. **Hak akses aktual:** verifikasi seluruh table/function grants, termasuk default privileges yang diwariskan. Migration belum menormalkan seluruh privilege pada anon/authenticated. Risiko privilege berlebih bersifat kondisional sampai grants database aktif diperiksa.
10. **Refresh sesi:** cabang redirect di proxy mengembalikan response baru tanpa meneruskan cookie yang mungkin baru diperbarui. Tinjau dan uji refresh menjelang kedaluwarsa serta redirect login/dashboard; belum dibuktikan gagal melalui browser.

## Urutan pembangunan

| Tahap | Hasil yang harus dicapai | Kriteria selesai |
| --- | --- | --- |
| 1 — Kontrol dasar | Matriks peran per operasi, izin proyek konsisten, metadata immutable, audit perubahan, administrasi anggota, validasi dan error form | Uji akses dua organisasi/tujuh peran lulus; owner terakhir terlindungi; input gagal dapat diperbaiki pengguna |
| 2 — Satu alur operasional lengkap | Klien → proyek → pekerjaan → penanggung jawab → progres → bukti selesai; detail/edit/arsip/filter/pagination | Satu pekerjaan nyata dapat diproses tanpa edit SQL manual; data dan hak akses konsisten |
| 3 — Approval terhubung | Pengajuan dan review berdasarkan kebijakan, versi dokumen, lampiran, keputusan atomik dan notifikasi | Pengaju tidak bisa menyetujui sendiri; API langsung tidak bisa melewati aturan; revisi dan review paralel aman |
| 4 — Keuangan inti | Akun/periode/saldo awal, jurnal dan posting, reversal, laporan dasar; lalu invoice/pembayaran sesuai proses | Debit=kredit dijamin database; posting tepat sekali; periode tertutup menolak posting; laporan dapat direkonsiliasi |
| 5 — Ekspansi bisnis | SDM lanjutan, pajak dari transaksi, KPI dan integrasi yang memang dibutuhkan | Setiap laporan ditelusuri ke sumber transaksi; sinkronisasi memiliki rekonsiliasi dan pemulihan kegagalan |

CI dan pengujian dibangun mulai tahap 1 serta diperluas bersama fitur. Tidak perlu menunggu seluruh enam modul lengkap untuk uji coba internal alur tahap 2. Penggunaan untuk transaksi keuangan menunggu kontrol dan pengujian tahap terkait selesai.

Prioritas modul setelah fondasi perlu menyesuaikan proses inti GSP: jenis usaha, jumlah badan usaha, jalur persetujuan, jenis dokumen dan sumber data lama belum dinyatakan di repository. Estimasi waktu/biaya belum dapat ditetapkan secara bertanggung jawab dari kode saja.

## Validasi audit

- `npm.cmd run typecheck`: lulus, exit 0.
- `npm.cmd run build`: lulus, exit 0; kompilasi, pemeriksaan TypeScript dan prerender selesai.
- `npm.cmd run lint`: lulus, exit 0, tanpa temuan.
- Tidak ada pengujian runtime per peran atau penerapan migration dalam audit ini.
- Build memperbarui next-env.d.ts secara otomatis; perubahan tersebut dikembalikan ke isi awal agar audit tidak mengubah source aplikasi.

Referensi pendekatan RLS: [Supabase Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security). Panduan Next.js yang dibaca berasal dari paket lokal `node_modules/next/dist/docs/`, khususnya authentication, error-handling dan proxy, sesuai AGENTS.md.
