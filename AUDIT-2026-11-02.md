### Pemeriksaan indikasi backdoor/kode merusak

- Tidak ditemukan service-role/secret key pada source aplikasi, pola private key/token rahasia yang dipindai, maupun file `.env` sensitif yang tercatat pada riwayat Git yang tersedia. `.env.local` saat audit hanya mempunyai nama variabel URL dan publishable key; nilai tidak dicetak ke laporan.
- Tidak ditemukan endpoint bypass login, pembuatan akun owner tersembunyi, perintah reset/hapus database dari aplikasi, pemuatan skrip remote arbitrer atau pengiriman data ke domain asing dalam jalur runtime yang ditinjau. Seluruh 476 URL resolved dependency berasal dari `registry.npmjs.org`; hal ini bukan jaminan seluruh dependency bebas kompromi.
- Jalur `execFile` PowerShell berada pada OCR Windows. Script berasal dari file repository tetap; nama/path sementara dibuat server, bukan perintah dari isian pengguna. Cleanup dibatasi direktori sementara berawalan `gsp-ocr-`. Tidak ditemukan indikasi command injection pada pola ini.
- HMAC/base64 pada mode Lihat sebagai merupakan mekanisme cookie pratinjau; akses owner diperiksa saat mengaktifkannya, dan server actions memeriksa mode read-only. Pratinjau tersebut hanya UI, bukan pengganti pengujian memakai akun role sebenarnya.
- Advisor menandai fungsi definer legacy. `rls_auto_enable()` yang juga diberi execute anon ditinjau: return type-nya event_trigger dan isinya mengaktifkan RLS pada tabel baru. Tidak ada dasar menyebutnya backdoor atau menyimpulkan dapat dipanggil sebagai RPC bisnis biasa. Hak execute yang tidak perlu tetap sebaiknya dicabut setelah menilai dependensi platform.

Pernyataan ini terbatas pada review terarah source, SQL/metadata dan dependency advisories. Tidak membuktikan komputer, ekstensi browser, seluruh isi node_modules, akun cloud atau rantai pasok bebas kompromi. Tidak dilakukan penetration test penuh, audit forensik host atau uji restore.

## Riwayat audit 2 November 2026

Bagian di bawah mempertahankan temuan saat itu sebagai riwayat. Status terkini, prioritas dan bukti yang berlaku adalah pembaruan 5 November di atas; beberapa temuan lama sudah ditutup oleh migration/perubahan sesudahnya.

## Ringkasan eksekutif

ERP GSP sudah memiliki fondasi teknis yang baik untuk autentikasi, isolasi organisasi, workflow dokumen, approval, dan pencatatan audit. Tes yang tersedia lulus. Namun, sistem masih berupa fondasi dan MVP; beberapa kemampuan yang kini terlihat di modul Akuntansi dan kasbon belum membentuk proses bisnis lengkap. Kesiapan produksi untuk transaksi akuntansi, penyelesaian kasbon, dan pelaporan resmi belum terbukti.

**Rekomendasi utama:** selesaikan keterlacakan migration/deployment, administrasi entitas dan periode, lalu bangun siklus jurnal sampai posting dan rekonsiliasi. Setelah itu tuntaskan pertanggungjawaban kasbon serta alur operasional yang dipilih perusahaan. Jangan menganggap laporan atau data yang tampil sebagai bukti bahwa alur tersebut sudah dapat dijalankan dari awal hingga akhir.

## Cakupan dan batas bukti

Audit membaca source aplikasi, konfigurasi, dokumentasi, seluruh migration SQL yang ada di working tree, dan tes. Working tree saat pemeriksaan berisi perubahan lokal yang belum di-commit, termasuk dua migration baru. Temuan menggambarkan isi working tree tersebut; ini bukan pernyataan bahwa perubahan sudah di-commit atau migration sudah diterapkan ke database aktif.

Database Supabase aktif, migration history dan grants aktual, konfigurasi Auth, deployment/CI eksternal, backup, monitoring, data produksi, serta kebijakan bisnis GSP tidak diverifikasi. Karena itu, ketiadaan implementasi dalam repository tidak selalu membuktikan fasilitas tersebut tidak tersedia di layanan eksternal. Audit ini bukan penetration test, audit kepatuhan pajak/PSAK, ataupun persetujuan untuk penggunaan produksi.

## Yang sudah berjalan baik

- Server memverifikasi sesi Auth; akses data menggunakan Supabase RLS dan konteks organisasi.
- Alur workflow menyimpan draft terpisah dari record resmi, memakai snapshot versi, mencegah pengajuan disetujui sendiri, dan mengeksekusi perubahan melalui transaksi database.
- Migration memperketat hak tulis langsung pada record bisnis. Ada tes isolasi organisasi, perubahan versi, approval, rollback, dan idempotensi untuk alur workflow umum.
- Migration terbaru menambahkan approval Manager → Finance untuk kasbon serta fondasi entitas legal, periode, jurnal double-entry, dan sejumlah view laporan.
- UI terbaru mulai menampilkan ringkasan operasional dan laporan akuntansi; batas MVP juga sebagian dijelaskan di README.

## Temuan dan rekomendasi prioritas

### P0 — Tetapkan satu sumber kebenaran untuk migration dan status deployment

README hanya mencantumkan migration sampai `20261030101500_payment_module.sql`, sementara working tree juga memuat `20261030123000_cash_advance_approval.sql` dan `20261031100000_multi_entity_accounting_foundation.sql`. Catatan deployment yang ada bertanggal 30 Oktober dan tidak membuktikan status penerapan dua migration berikutnya. Kedua migration baru juga belum terlacak Git saat audit.

**Dampak:** instalasi baru yang mengikuti README dapat kehilangan fitur kasbon/akuntansi; upgrade pada database aktif berisiko menjalankan urutan yang salah atau menganggap schema aktif sama dengan source.

**Buat sebelum rilis:**
1. Putuskan migration mana yang merupakan perubahan final dan pastikan semuanya terlacak di Git.
2. Perbarui urutan instalasi, prasyarat, prosedur upgrade, verifikasi hasil, dan catatan database aktif.
3. Uji instalasi dari database kosong dan upgrade dari versi yang benar-benar aktif. Jangan mengulang migration pada deployment yang sudah menerapkannya.
4. Catat hasil penerapan per lingkungan serta mekanisme pemulihan/rollback yang sesuai untuk migration tersebut.

### P1 — Lengkapi fondasi akuntansi menjadi proses yang dapat dijalankan

`20261031100000_multi_entity_accounting_foundation.sql` membuat tabel jurnal/baris jurnal dan view buku besar, tetapi hak tulis dicabut dari klien. RPC yang tersedia adalah posting jurnal yang sudah ada; tidak ditemukan RPC/UI untuk membuat draft jurnal dan barisnya. Halaman Akuntansi mengambil data laporan, sedangkan pengaturan entitas/cabang disebut belum tersedia di UI. Akibatnya, dari aplikasi pengguna belum dapat mengelola seluruh jalur entitas → periode → jurnal → posting.

Migration juga belum menyediakan alur administrasi periode (pembuatan/penutupan), pembalikan jurnal yang dapat dieksekusi, sumber posting dari transaksi modul, rekonsiliasi bank, maupun penyajian formal neraca/laba-rugi. View `trial_balance` merupakan ringkasan saldo dari jurnal posted, bukan pengganti laporan formal yang telah dipetakan dan disetujui.

**Bangun secara berurutan:**
- administrasi bagan akun, entitas/cabang, keanggotaan entitas, periode, dan saldo awal;
- form/API draft jurnal dan baris dengan validasi akun, entitas, periode, mata uang, dimensi dan sumber transaksi;
- posting atomik, nomor jurnal, audit, idempotensi, kontrol periode tutup, dan jurnal pembalik;
- rekonsiliasi subledger dan bank terhadap buku besar;
- laporan keuangan dengan pemetaan akun dan kebijakan yang disetujui perusahaan.

**Syarat rilis keuangan:** debit = kredit diuji di database, posting tidak ganda, periode tertutup menolak jurnal, koreksi posted dilakukan dengan reversal, dan saldo laporan dapat direkonsiliasi ke sumber transaksi.

### P1 — Selesaikan siklus kasbon sampai pertanggungjawaban

Migration kasbon mengatur approval bertahap Manager → Finance dan eksekusi yang membuat kewajiban pembayaran. Pembayaran kewajiban yang ditandai lunas memperbarui status kasbon menjadi `disbursed`. Namun status `settled` belum memiliki alur aplikasi/RPC; tidak ditemukan pencatatan realisasi biaya, bukti pertanggungjawaban, atau penutupan kasbon.

**Dampak:** persetujuan dan kewajiban pencairan belum menjawab apakah uang benar-benar diterima, biaya aktualnya berapa, ada sisa/kelebihan dana, atau apakah kasbon sudah dipertanggungjawabkan.

**Buat:** pencatatan pencairan aktual, unggah bukti privat, laporan realisasi per kategori/proyek, persetujuan pertanggungjawaban, pengembalian sisa atau penagihan kekurangan, tanggal jatuh tempo dan pengingat, penutupan yang tidak dapat diulang, serta posting jurnal yang dapat ditelusuri. Tetapkan perlakuan uang muka dan batas nominal bersama Finance sebelum implementasi.

### P1 — Selesaikan model akses untuk organisasi dan multi-entitas

`requireWorkspace()` memilih satu membership dengan `limit(1)` tanpa pilihan organisasi aktif. Migration entitas membatasi pembacaan beberapa laporan dengan `entity_memberships`, tetapi tabel bisnis operasional tetap berlingkup `organization_id` dan komentar migration menyatakan data operasional belum dibatasi per entitas.

**Dampak:** pengguna yang menjadi anggota beberapa organisasi tidak dapat memilih konteks secara eksplisit; sementara akses laporan per entitas belum berarti akses CRM, proyek, aset, pembayaran, atau SDM juga terisolasi per entitas.

**Buat:** pemilih organisasi/entitas aktif yang divalidasi di setiap request dan server action; layar admin untuk membership/role; definisi apakah entitas hanya dimensi laporan atau batas akses bisnis; lalu selaraskan RLS seluruh modul, report, ekspor, dan pengujian dengan keputusan tersebut. Audit perubahan membership dan role.

### P1 — Pertahankan hak auditor sebagai read-only pada kasbon

README menyatakan auditor hanya-baca, tetapi konfigurasi kasbon pada `src/lib/workflow.ts` dan `gsp_private.record_config('advance')` di migration memasukkan `auditor` ke daftar `writers`. Dengan demikian auditor dapat membuat dan mengajukan kasbon, meskipun tetap tidak dapat menyetujui pengajuannya sendiri.

**Perbaiki:** keluarkan auditor dari daftar penulis pada UI dan database, lalu tambahkan tes negatif yang membuktikan auditor tidak dapat menyimpan atau mengajukan draft. Tetapkan secara eksplisit role mana yang berhak mengajukan kasbon dengan pemilik proses perusahaan.

### P1 — Tambahkan tes perilaku spesifik fitur yang baru

Validasi audit ini lulus: `npm run lint`, `npm run typecheck`, `npm run test:auth` (5 tes), `npm run test:workflow` (17 tes), dan `npm run test:dashboard` (4 tes). Tes workflow menjalankan seluruh migration dalam PGlite, tetapi cakupan assertion yang ada berfokus pada lifecycle workflow umum. Script UI untuk workflow umum tersedia, tetapi tidak ditemukan tes assertion khusus untuk urutan approval kasbon, pertanggungjawabannya, administrasi/akses entitas, pembuatan jurnal, posting jurnal, penutupan periode, atau laporan akuntansi. Tidak ditemukan konfigurasi CI di repository.

**Buat:** tes integrasi database untuk skenario sukses dan penolakan di atas; tes tenant/entity lintas organisasi; tes konkurensi posting/approval pada PostgreSQL yang mendukung koneksi paralel; tes UI untuk alur kasbon dan akuntansi; serta CI yang menjalankan lint, typecheck, seluruh tes, dan build. PGlite berguna untuk pengujian cepat tetapi tidak menggantikan uji perilaku PostgreSQL deployment.

### P2 — Siapkan operasi produksi dan tata kelola data

Repository tidak cukup untuk membuktikan konfigurasi produksi. Verifikasi secara eksplisit MFA untuk peran sensitif, kebijakan sesi dan pemulihan akun, rate limit, backup dan uji restore, pemantauan error/database, staging terpisah, rotasi secret, retensi audit/lampiran, serta runbook insiden dan perubahan schema. Lampiran belum tampak sebagai alur aplikasi; bila diperlukan, buat storage privat dengan kebijakan akses per organisasi, batas ukuran/jenis file, retensi, dan penghapusan yang diaudit. Jangan menyimpan secret integrasi dalam browser.

## Urutan kerja yang disarankan

| Tahap | Hasil | Kriteria selesai |
|---|---|---|
| 0. Siapkan rilis | Status migration dan deployment tegas; panduan instalasi/upgrade benar; CI dasar | Database kosong dan upgrade teruji; setiap lingkungan memiliki catatan versi |
| 1. Tetapkan akses | Model organisasi/entitas, pemilih konteks, admin membership, matriks izin | Tes allow/deny per organisasi, entitas, role dan endpoint lulus |
| 2. Tutup proses operasional | Satu alur CRM/proyek/pekerjaan atau kasbon lengkap sesuai prioritas bisnis | Pengajuan sampai penutupan bisa dilakukan di UI tanpa SQL manual dan memiliki audit trail |
| 3. Aktifkan akuntansi | Admin periode/akun, jurnal, posting, reversal, rekonsiliasi dan laporan tervalidasi | Saldo dapat ditelusuri dan direkonsiliasi; uji concurrency dan periode tutup lulus |
| 4. Perluas modul | SDM, pajak, integrasi dan KPI berdasarkan kebutuhan yang disahkan | Setiap fitur memiliki owner, aturan, hak akses, bukti, dan tes penerimaan |

## Kesimpulan

Fondasi workflow dan tes umum memberi titik awal yang baik. Kesenjangan terbesar saat ini bukan menambah banyak menu, melainkan menuntaskan siklus bisnis, administrasi, dan pembuktian hasil—terutama untuk accounting, kasbon, dan cakupan entitas—serta memastikan migration yang direncanakan sama dengan database yang akan dijalankan. Perlakukan fitur tersebut sebagai **belum siap produksi untuk transaksi terkait** sampai kriteria pada temuan P0/P1 dipenuhi dan diverifikasi pada lingkungan deployment.
